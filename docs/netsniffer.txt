Integrating the netsniffer into LEGION2

    Turn it into a pipeline Source

        Wrap the sniffer in a struct (e.g., NetsnifferSource) that implements the Source trait.

        The start method should open the pcap capture, apply BPF filters, parse packets with etherparse, and convert each interesting packet into an Observation (Host, Service, Metric, etc.).

        Use a channel or futures::stream::unfold to produce an ObsStream just like the NmapScanner or MasscanScanner sources.

    Stream observations instead of writing NDJSON directly

        Move the existing PktMeta capture logic into an async loop that pushes Observation objects.

        Example mapping:

            TCP SYN‑ACK → ObservationKind::Service with fields {ip, port, protocol, state: "open", ttl, vendor…}

            Unique source IP without known host → ObservationKind::Host

            Optional metrics (packet count, bytes) → ObservationKind::Metric.

        Persist raw packet metadata only when needed (e.g., evidence). Use the existing log_artifact helper for NDJSON if you want on‑disk copies.

    Register the sniffer with the registry

        Add a Plan::netsniffer builder (similar to Plan::masscan) that sets source_type to "netsniffer".

        Extend Registry::initialize_standard_components and Registry::create_source to include "netsniffer" so it becomes selectable via engine_execute(plan).

    Feed data to the UI and DB

        Once NetsnifferSource emits observations, the existing UiSink will turn them into Tauri events (obs:host, obs:service, obs:metric) automatically.

        DbSink will persist host/service rows as long as the observation fields contain ip, port, protocol, etc.

        No frontend code changes are required beyond exposing a “netsniffer” option when building scan plans.

    Capture multiple protocols / IoT “back‑noise”

        Expand the sniffer loop to handle UDP, ICMP, and ARP packets.

        Each protocol should map to a minimal Observation (e.g., SSDP replies → Service observations with service: "upnp").

        The large OUI table already provides vendor enrichment.

        To actively “bounce around” IoT devices, integrate small UDP probes (SSDP, mDNS, NetBIOS) from scanners/probes/ and emit them via a companion probe_* function, capturing responses through the same sniffer pipeline.

    Channel future enhancements into transforms

        If packet parsing grows complex, split it into transforms:

            ServiceParsingTransform for protocol detection,

            IpEnrichmentTransform for OUI/geo/ASN lookups,

            ProgressTrackingTransform for metrics.

Frontend visibility & network mapping

    The React store already listens for obs:* events; once the sniffer is registered and producing observations, hosts and services will populate automatically in HostTable, NetworkMap, and other views.

    For real-time network mapping, emit TopologyEdge observations whenever the sniffer sees communication between two hosts (source/destination IP pairs).

    Consider sending periodic Metric observations (packet counts, discovery rate) so the UI can display sniffer performance.

Using the existing probes directory

    The scanners/probes/ directory contains reusable probe logic (SSDP, mDNS, NASL snippets, etc.).

    Extract small request builders (e.g., UDP payloads) and trigger them from NetsnifferSource or a dedicated transform when certain packet types are observed.

    Responses flow through the same sniffer → observation pipeline, giving you lightweight “active” reconnaissance without external tools.

With these steps, the netsniffer becomes a first-class engine Source, feeding observations into the same pipeline as masscan and nmap, allowing the frontend to display and analyze traffic live.
